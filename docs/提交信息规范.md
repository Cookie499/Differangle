# Git 提交信息规范

为了保持提交历史的清晰、可读，团队采用统一的提交信息格式。

## 格式

<类别>[(<相关的功能或类>)]: <对本次提交的总结>

- 类别：见下方定义，不可省略。
- 相关的功能或类（可选）：用括号包裹，表示本次提交影响的模块、系统、类或包。例如 (block)、(item)、(entity)。可以用逗号分隔多个影响的模块、系统、类或包，不宜过多。
- 总结：简要描述本次提交做了什么，使用中文，推荐动词开头（如“增加”“修复”“调整”）。

如果本次提交涵盖了多方面的内容，可以用分号分隔不同的总结，但建议尽可能保证每次提交只做一件事。

### 示例

feat(decoration): 增加铜管道方块（装饰方块）
fix(pathfind): 修复实体寻路处理 stepHeight 不正确的问题
tweak(ChestHider): 调整箱子怪对被追杀过的玩家的愤怒值上限
test(CollectionUtil): 为 selectByWeight 方法编写单元测试
resource(ChestHider): 增加箱子怪的 ON_ATTACK 动画

## 类别定义

| 类别 | 含义 | 使用场景 |
|------|------|----------|
| feat | 新功能或修改现有功能 | 新增某个系统/功能，或改变已有功能的逻辑、行为（不是 bug 修复也不是数值微调） |
| fix | 修复 Bug | 修复任何预期外的问题、崩溃、逻辑错误等 |
| refactor | 重构 | 在不改变外部行为的前提下，改进代码结构、可读性、可维护性（注意资源文件位置整体移动且不修改功能也属于这一类别，而不属于 resource 类别） |
| perform | 性能优化/表现优化 | 优化代码性能，减少内存、CPU 或 IO 消耗；或是优化表现，提升用户体验（可能会与 feat 类别重合，看本次提交你的主观意愿是什么，如果主要是为了优化表现那就归入 perform 类别） |
| tweak | 数值/参数微调 | 仅修改常量、配置参数、数值，不改变功能逻辑或结构。典型例子：调整速度值、生成概率、伤害系数等 |
| test | 测试相关 | 编写单元测试、集成测试、测试用命令、测试辅助类或任何为了验证功能正确性而添加的测试代码 |
| docs | 文档 | 仅与文档相关，如 README、代码注释、JavaDoc/KDoc、Wiki 的更新 |
| config | 项目配置 | 修改构建脚本（Gradle/Maven）、依赖、IDE 设置、CI/CD 配置等 |
| misc | 杂项 | 不符合以上任何类别的小修改（例如临时调试代码、格式化空白、提交工具脚本等） |
| resource | 游戏资源文件 | 提交纹理贴图（PNG）、模型（JSON）、音效（OGG）、语言文件、数据包（datapack）等 Minecraft 模组开发中特有的非代码资源 |

## 补充说明

1. 提交总结：应清晰说明“做了什么”，可以适当简要描述这么做的“原因”。
2. 原子提交：每次提交尽可能只做一件事，避免把多个类别的修改混在一起。
3. 可选范围：尽量填写，有助于快速定位影响面。例如 feat(worldgen): 将新增的结构加入到世界生成中
5. 表现优化与修改现有功能的处理：如果你觉得这次提交的主要目的是为了提升性能或用户体验，那么就归入 perform 类别；如果你觉得这次提交的主要目的是为了修改功能逻辑或行为，那么就归入 feat 类别。这个没有绝对标准，主要看你的主观意愿是什么。
6. 数值调整 vs 功能修改：  
   - 只改常量字段`const val`/`static final`，或者修改默认配置文件中的数值 -> tweak
   - 修改了判断逻辑、流程，或者是添加/删除了代码 -> feat 或 fix
7. 修复 Bug 与修改功能的区分：  
   - 代码行为偏离了设计预期，进行修正 -> fix  
   - 设计本身要调整，代码按新意图修改 -> feat
8. test 类别专门用于提交测试相关代码。如果同时修改了生产代码和测试代码，应当视主要内容决定类别，但推荐分开提交（先改功能后补测试）。
9. refactor 类别仅限于不改变外部行为的代码重构，不要把什么修改都塞到这个类别里来。比如将一个硬编码的数值改成一个常量字段或加进配置文件，将一个枚举类改造成注册项，移动类的位置，修改变量名/类名/包名，这些都属于不改变外部行为的代码重构，归入 refactor 类别；如果你改了代码的逻辑、流程，或者是添加/删除了代码，那么就不属于 refactor 类别了，应该归入 feat 或 fix 类别。另外，进行 refactor 类别的提交时，很有可能会引起合并冲突，建议进行重构前先于其他人商量好，或者在重构完成后尽快合并到主分支，以减少冲突的可能性。
10. resource 类别专门用于提交 Minecraft 模组开发中特有的非代码资源文件。如果同时修改了代码和资源文件，应当视主要内容决定类别，但推荐分开提交（先改代码后改资源，或者反过来）。如果你改了资源文件的位置但没有改动它的内容，那么就属于不改变功能的代码重构，归入 refactor 类别；如果你改了资源文件的内容，那么就不属于 refactor 类别了，应该归入 resource 类别。
11. misc 类别适用于那些不符合以上任何类别的小修改，例如临时调试代码、格式化空白、提交工具脚本等。其实本来打算给“提交工具脚本”单开一个类别的，但我感觉类别有点多了，还是放在 misc 类别里吧。总之，如果你觉得你的提交不太好归类，或者是一些很小的修改，就可以考虑用 misc 类别。
12. 善用分批提交。IDEA和VSCode都可以选择你要提交的文件和具体的改动行来进行提交，这样就可以很方便地把不同类别的修改分开提交了。比如你改了一个功能的代码，同时也改了它的测试代码，那么你就可以先提交功能代码，类别是 feat；然后再提交测试代码，类别是 test。这样就能保持提交历史的清晰和可读性了。
13. 以上要求并不是硬性要求，你写错了也不会追究你，顶多是提醒你一下。主要是为了养成一个良好的提交习惯，保持提交历史的清晰和可读性。

## 快速查询表

| 你做了什么 | 该用什么类别 |
|-----------|--------------|
| 添加了一个新方块、新物品或新机制 | feat |
| 修改了某个功能的逻辑（不是修 bug） | feat |
| 修了一个崩溃或逻辑错误 | fix |
| 优化代码结构，功能不变 | refactor |
| 让生成世界或渲染更快，优化视觉效果 | perform |
| 改了几个数值（如速度、概率、强度） | tweak |
| 写了一个测试类或测试命令 | test |
| 修改了 README 或添加了函数文档 | docs |
| 修改 Gradle 配置，新增或升级项目依赖 | config |
| 提交了一张纹理、一个模型或一个音效文件 | resource |
| 改了缩进或导包排序（无其他改动），添加了工具脚本 | misc |
