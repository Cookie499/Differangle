# 多屏幕高分辨率、高刷新率性能梳理

日期：2026-10-10。范围：当前 Texture / Embedded、Sodium 0.9.1 / Iris 1.11.2 路径。

这是代码审计与优化设计，含用户提供的 FPS 读数，不是控制变量下的性能实测报告。此前 BSL 客户端测试验证了正确性和资源生命周期，没有测量持续吞吐或帧时间分布。

## 用户补测与当前判断

确认场景：Texture、开启摄像机光影、三个屏幕绑定同一台摄像机；摄像机和屏幕的 FPS 都做了修改。

| 用户测量 | 游戏 FPS |
| --- | --- |
| 屏幕全关，垂直同步 | 240（封顶，不能当作无帧率限制的基线） |
| 默认 256×144、配置 15 FPS，初次补测 | 约 150–180 |
| 配置 60 FPS，初次补测 | 约 100 |
| 调整到 1440×960，初次补测 | 没有明显进一步下降 |
| 光影与屏幕开启，配置 15 FPS，后续确认 | 约 114 |
| 同一测试调整摄像机和屏幕到 60 FPS，后续确认 | 约 45 |

两轮绝对 FPS 不同，应分别保留，不能混合拟合单次渲染耗时。提高刷新率显著变贵、提高分辨率未显著变贵，支持优先调查每次摄像机更新的固定成本：地形扫描、CPU/驱动提交、固定尺寸阴影与场景遍历。不能仅凭这些 FPS 判断 CPU 或 GPU 哪个已饱和，也不能断言后处理完全不重要。

1440×960 的像素数是默认分辨率的 37.5 倍，但宽高比也从 16:9 改成 3:2，正式像素成本测试应保持宽高比一致。垂直同步封顶会掩盖基线余量，后续性能采样应关闭垂直同步/帧率上限并充分预热。

一台摄像机绑定三个屏幕，仍只刷新一幅摄像机画面。此前“三台摄像机的管线成本/调度上限”不是本次主要解释；三个外壳加一台非隐藏调试摄像机的辅助几何是 108+66=174 次通道，不是三台摄像机时的 306 次，实际还取决于摄像机是否隐藏。

配置 60 FPS、游戏只有 45 FPS 时，此实现每主帧最多刷新摄像机一次，实际屏幕刷新率不可能达到 60，最多约 45；配置值必须和实际刷新率区分。

首轮修改已消除 Iris 路径中的重复基础地形准备，统一收集原生列表/方块实体/动画精灵，复用同次刷新的虚拟相机、region 排序和 uniform 更新。阴影、图像分辨率、更新率与光影效果没有降级。辅助几何合批、GPU 分段计时和阴影缓存仍待实施；尚无修改前后持续性能对比，不能承诺具体 FPS 提升。

验证结果：构建与 38 项单元测试通过；BSL 客户端回归通过双摄像机移动、分辨率修改、资源重载、Iris 关闭/开启、方块实体，以及三屏共享单台 1440×960 摄像机（配置 60 FPS）的 Texture 与 Embedded 溢出路径。已检查共享屏幕截图。测试没有以实际输出 60 FPS 作为通过条件，不作为性能提升证据。

## 结论

保留 Texture 作为高性能主路径，先消除无画质损失的 CPU / 提交浪费，再优化每台摄像机的阴影、可见性和后处理。高分辨率、高刷新率需要摄像机单次更新足够便宜，单纯提高更新数量上限只会加重负载。

三个屏幕必须分成三个案例：

- 同一摄像机：当前已经共享图像，每次刷新只渲染一次世界。主要增加的是屏幕/外壳合成，另有共享摄像机按所有启用屏幕的最高要求升级分辨率与 FPS 的情况。
- 三台独立摄像机：每台都要维护和执行自己的视角、阴影及 Iris 后处理，不能把不同视角直接当作同一幅图复用。
- 三面镜子：当前是独立更新路径，最多每主帧更新两面；没有按屏幕配置的 FPS 检查截止时间。不能套用普通摄像机的调度结论。

## 已确认的代码开销

### 1. 外壳、支架、调试线框拆成大量 RenderPass

位置：`WorldGeometry.housing/debug/line/cube`、`CameraCompositor.solid`、`CameraRuntime.renderNow`。

每个立方体拆成六次 `solid()`，每次独立创建 RenderPass、写 uniform、绘制六个顶点。

- 一个屏幕外壳：背板一个立方体、四条边框四个立方体、支架一个立方体，共 36 次 RenderPass。
- 一台非 Invisible 摄像机的调试显示：三条轴线和八条视锥线，共 11 个立方体，即 66 次 RenderPass。
- 三个屏幕和三台启用调试显示的摄像机：辅助几何 306 次；屏幕背景和图像另加最多六次。这还不包括摄像机世界与光影。

上述数字是代码路径计数，不是 GPU 时间；被深度测试挡住也已经发生 CPU 提交。当前遍历全部已加载屏幕绘制外壳，调试几何也没有主视角视锥过滤。

优化：使用真实立方体三角网格，将全部可见不透明外壳和调试几何批量绘制；缓存静态世界几何或实例数据，先做几何包围盒剔除。保留原有颜色、深度、凹入量和支架外观。调试可增加显式开关，但默认关闭属于产品行为变更，不作为唯一优化手段。

验收：辅助几何的通道数不再按每立方体六次增长；遮挡、相邻屏幕边框与画面覆盖关系不变。

### 2. 光影路径重复准备地形（首轮已消除）

位置：`CameraWorldRenderer.prepare`、`SharedTerrainRenderer.prepare`、`SodiumTerrain.prepare`、`IrisShaderCameras.CameraTerrain`。

修改前先执行基础后端的 Sodium 区块扫描，读取网格头、按面建立 TerrainDraw、写 section uniform；随后 Iris 光影后端再次扫描相同半径的区块并建立 ChunkRenderList。基础 TerrainDraw 在此光影路径中没有用于绘制，但准备结果中的方块实体仍然被使用。现在 Iris 准备直接生成原生列表和元数据，不再展开基础绘制数据；Embedded 及其 Texture 溢出缓存分别准备对应后端数据。

优化：在准备阶段明确后端，使用一次摄像机可见性遍历同时产出统计、方块实体和后端需要的数据。Iris 路径直接产生原生 ChunkRenderList，基础路径才展开 TerrainDraw。不能简单跳过全部基础准备，否则会漏掉摄像机内的方块实体。

验收：光影每次摄像机刷新只遍历一次候选区块；地形、动画材质、方块实体都保持正确。

### 3. 候选区块范围与主视角视距绑定，缺少摄像机遮挡剔除

位置：`SodiumTerrain.prepare`、`IrisShaderCameras.CameraTerrain.init`。

两条路径都按主视角 effectiveRenderDistance 扫描摄像机周围的 X/Z 范围及整段世界高度，然后逐段做视锥判断。没有利用摄像机自己的遮挡结果。室内、地下或背后大量区块可能仍进入绘制。

优化分两步：

1. 保留摄像机自己的可见性，先按 region 粗剔除、再逐 section 判断；按区块加载/卸载、网格重建和摄像机视锥变动管理缓存。
2. 视实测决定是否接入摄像机独立的遮挡遍历，或基于自己深度的分层深度遮挡。采用历史结果必须在移动、显露或网格变化时保守失效，防止闪洞。

可增加独立视距以适配监控室等场景，但这会改变远景质量，应由用户选择。不能复用玩家的可见区块列表，否则玩家转身会使远程屏幕缺块。不能把共享 Sodium 区块对象交给工作线程无保护读取。

### 4. 每次摄像机刷新都调用完整阴影与后处理

位置：`IrisShaderCameras.draw`，特别是 `renderShadows`、`beginTranslucents`、`finalizeLevelRendering`。

每台摄像机有独立 IrisRenderingPipeline。降低图像分辨率可以减少部分像素工作，但不会按相同比例降低区块扫描、实体提取、阴影遍历或固定尺寸阴影贴图的成本。

这是需要 GPU 分段测量的主要候选瓶颈，尚不能断言它占当前损失的具体百分比。

长期设计：

- 完整兼容模式保留任意受支持光影包的渲染语义。
- 为高性能需求提供经过适配的摄像机光影路径，允许阴影与最终图像以不同频率更新。缓存必须同时保留阴影矩阵、纹理及光影包依赖的状态，不能只是跳过一次 `renderShadows`。
- 移动、太阳变化、动态遮挡物、世界修改必须触发相应失效；降低阴影频率会引入阴影延迟，是有明确质量代价的选项。
- 只有覆盖区域、光照和投影条件满足时，研究附近摄像机共享阴影。远程摄像机不能直接借玩家阴影，独立曝光和 TAA 历史也不能随意共用。
- 如果必须保证三路真实高分辨率、高 FPS，长期重点应是受控的摄像机渲染后端，而不是假设通用 Iris 管线可以无成本复制三份。

### 5. 当前调度硬上限不满足多路高刷新率

位置：`CameraSystem.maxUpdatesPerFrame/renderFrame`、`CameraRuntime` 镜子更新分支。

普通 Texture 默认每主帧最多更新一台摄像机，因此所有普通摄像机的实际更新率之和不会超过游戏主帧率。三台持续可见、同等优先级摄像机在主画面 60 FPS 时，理论上限约为每台 20 FPS；配置成 60 不会改变这个上限。刷新截止时间与主帧采样还可能进一步减少实际更新率。

镜子最多每主帧更新两面，而且当前没有按屏幕 FPS 限速。Embedded 每主帧直接渲染最多两个屏幕，其他屏幕走 Texture；即使绑定同一摄像机，直接屏幕仍重复绘制世界。

优化：

- 为普通摄像机和镜子建立统一的截止时间调度，保留不同视角的资源独立性。
- 支持根据实测 GPU 成本和目标主帧预算，决定每帧更新数量；缓存图像仍每主帧合成。
- 持续显示每台实际更新率、图像年龄与丢失截止次数，明确区分“配置 60”与“实际 60”。
- 如果算力充足，允许一主帧更新多台；若不充足，预算只能维持主画面稳定，不能同时创造三个真实 60 FPS 输出。

### 6. 次级 CPU / 内存开销

- 每个光影视图构造多次 VirtualCamera，重复初始化环境探针并建立临时 Marker。
- 每台摄像机重复扫描实体并提取渲染状态；一些模型/动画结果可能共享，但距离、朝向和视角相关状态必须独立。
- Iris 不透明和透明绘制重复排序 region、更新 uniform、清理批次。可复用同次刷新的有序列表，批次缓存隔离必须正确，不能直接移除当前防止污染主视角的清理。
- 无 Sodium 的原版半透明路径逐 section 重排索引、创建并关闭 GPU 缓冲区；后续可做缓冲复用。
- 同一摄像机的分辨率/FPS 需求由所有启用屏幕决定，即使最高规格屏幕不在主视角内。可按实际可见需求选择工作分辨率，但需要稳定档位、迟滞与历史重建策略，避免重新引入频繁重建问题。

这些排在主要渲染与提交成本之后，通过测量决定取舍。

### 7. 摄像机运动采样频率与画面刷新率没有解耦

位置：`CameraRuntime.tick`、`WorldClient.tick`、`CameraEntity.snapshot`。

实体摄像机的 CameraDefinition 在客户端 tick 时更新，直接使用实体的当前位置与同步四元数，没有在每次渲染时根据 partial tick 插值摄像机姿态。正常 20 TPS 下，即使屏幕实际绘制 60 FPS，镜头轨迹也可能每秒只改变约 20 次；世界中的实体可以有帧间插值，但镜头运动仍呈阶梯。

优化：保留权威 tick 姿态和前后样本，在摄像机刷新前对位置和四元数插值，明确瞬移/step 路径的断点策略；每次刷新所有阶段使用同一姿态快照。插值必须复用原 Target/管线，不能把每个插值姿态当成资源失效。高 FPS 验收同时检查画面更新与镜头运动的连续性。

## 应先建立的测量

现有 `cpuMillis` 是从 renderNow 开始到清理结束的 CPU 侧墙钟时间，包含提交和可能的驱动等待，不代表 GPU 完成所用时间；`drawCalls` 主要来自地形统计，也没有覆盖全部外壳、阴影和后处理。

当前 Minecraft 26.2 的本地 Blaze3D 源码已提供：

- `GpuDevice.createTimestampQueryPool`
- `CommandEncoder.writeTimestamp`
- `GpuQueryPool.getValues`，以 OptionalLong 表示尚未就绪
- `TimerQuery`，可参考其周期和状态管理，但自定义分段计时应避免与主帧查询相互覆盖

建议分别记录 CPU 与异步 GPU 时间：辅助几何、地形准备、阴影、地形绘制、实体/粒子、deferred/composite/final、屏幕合成。延后读取已就绪的查询，队列满时跳过采样，不能强制等待 GPU 取回当前帧结果。

查询异步读取与同步阻塞的区别见 [Khronos Query Object 文档](https://wikis.khronos.org/opengl/Timer_Query)。

每组固定视角、天气、实体和窗口尺寸；先完成区块加载与光影预热，再持续采样至少 30 秒，报告帧时间中位数/P95/P99、各摄像机实际 FPS/画面年龄、显存/管线数量、错误及重建次数。镜头静止和连续移动分别测量。

建议测试矩阵：

| 对比 | 目的 |
| --- | --- |
| 0 屏幕 / 1 屏幕 / 3 屏幕，同一摄像机、固定最高规格 | 分离显示合成与摄像机世界更新 |
| 1 / 3 台摄像机，固定分辨率、实际更新总量 | 分离多管线驻留与每次刷新成本 |
| 相机光影开/关，主视角光影保持不变 | 判断摄像机光影的增量成本 |
| 256×144 / 1280×720 / 1920×1080，同一实际刷新率 | 区分像素成本与固定 CPU/阴影成本 |
| 辅助几何单独开/关；合批前后 | 验证大量 RenderPass 的影响 |
| 屏幕在视锥外 / 在视锥内但被墙挡住 | 验证当前可见性与新增遮挡策略 |

三路 1920×1080、真实 60 FPS 每秒需要输出 373,248,000 个摄像机像素；这是单个最终输出层的像素量，尚未计阴影、透明叠加、多层 G-buffer 和后处理。相同 FPS 下，1080p 的像素数是默认 256×144 的 56.25 倍，不能把默认分辨率下的性能外推成高分辨率保证。

## 推荐实施顺序与验收

1. **建立基线并合批辅助几何**：补分段计时与实际 FPS；合并外壳/调试绘制并做视锥剔除。这一步保留画质和刷新率。
2. **统一地形准备**：Iris 避免基础 TerrainDraw 的无效展开；一次遍历产出原生列表和方块实体；缓存 region/section 候选与矩阵无关数据。
3. **按测量优化 GPU 热点**：优先处理实际最贵的阴影/后处理；通用兼容与受控高性能后端明确分开，保持独立历史。
4. **升级统一调度**：在单次更新足够便宜之后放开多摄像机更新，并按预算保护主画面。验证三台都达到目标实际 FPS，而非只提高配置数值。
5. **再考虑降采样、重投影、多视图等进阶方案**：升采样得到的是高分辨率输出，重投影得到的是合成帧，均需单独标注。多视图需要后端和光影配合，不能当作现有 Iris 管线的简单开关；不同视角的片元与后处理工作仍然存在。相关概念见 [Khronos 多视图说明](https://github.khronos.org/Vulkan-Site/tutorial/latest/OpenXR_Vulkan_Spatial_Computing/08_Slang_Spatial_Shaders/01_introduction.html)。

每一步同时跑已有正确性回归与固定场景性能对比。保留截图检查透明、水、阴影、远程实体、相邻边框、主视角恢复和连续移动，防止通过漏画内容获得表面上的提速。

总帧预算以目标硬件实测为准：60 FPS 一帧约 16.67 ms，120 FPS 约 8.33 ms。如果主世界和辅助绘制已经耗尽预算，三路完整光影的真实高分辨率/高 FPS 无法仅凭调度实现；必须减少重复工作、改变相机渲染后端/效果成本，或增加算力。
